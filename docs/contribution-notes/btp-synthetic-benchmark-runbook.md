# BTP synthetic benchmark operations

The workflow `BTP synthetic benchmark` is report-only. It builds the exact reviewed provider revision and runs one serial create/Ready/delete observation for Subaccount, Directory, Entitlement, DirectoryEntitlement, and SubaccountApiCredential against a **dedicated, approved SAP BTP test account**. It is not a performance gate or a statistical performance test. A healthy report has `status: not_evaluated`; missing lifecycle evidence or any operation/cleanup failure fails the job. The expanded workload must not be enabled for scheduled or routine CI use until the trusted-host acceptance and account-owner feasibility gates in `btp-multi-resource-benchmark-plan.md` are complete.

## Required setup before enabling runs

1. Provision a dedicated BTP test account with sufficient Subaccount, Directory, entitlement, and credential quotas in region `eu10`. Confirm account permissions, billing responsibility, a human cleanup contact, and conservative per-resource limits. Directory requires two distinct admins; confirm both are valid users in the account. Confirm `cis/local` is available for both Subaccount and Directory entitlements without allocation conflicts; choose another account-owner-approved low-cost plan or defer the relevant test if it is not. Do not use a developer or production account.
2. Configure GitHub environment `pr-e2e-approval` with required reviewers. Every PR run, including fork PRs, waits for explicit review before checkout/build or secret access. A changed PR head fails the stale run; the new push must receive fresh review.
3. Configure `pr-e2e-no-approval` variables `GLOBAL_ACCOUNT` (the dedicated global account subdomain) and `CLI_SERVER_URL` (the BTP CLI server URL for that environment), and secrets `BTP_TECHNICAL_USER`, `CIS_CENTRAL_BINDING`, `TECHNICAL_USER_EMAIL`, `SECOND_DIRECTORY_ADMIN_EMAIL`, and `XP_DIADROMOS_RELEASE_TOKEN`. The account subdomain must match the global account that owns the CIS central binding. The two admin email secrets must identify distinct, valid BTP users. Use the provider's established JSON credential formats. The release token should be a short-lived GitHub App installation token or fine-grained credential with only Contents: read on the private xp-diadromos repository. Never put credential material into config, scripts, artifacts, or logs.
4. Confirm private action access and authenticated v0.7.1 asset installation in a trusted manually approved default-branch dispatch. A successful local syntax check does not prove the private action can be fetched or the release token works.

## Resource ownership and discovery

Every workload object is named with a run-unique suffix derived from the explicit `XP_DIADROMOS_BTP_RUN_ID`, attempt, and timestamp. The Subaccount uses `xp-btp-bench-` plus that suffix and the BTP subdomain uses `xpbtpbench-`; Directory, both entitlements, the API credential, and its generated connection Secret each have distinct names containing the same suffix. The Directory display name is run-unique. Find the GitHub run ID/attempt in the workflow URL or run summary; for local runs record the supplied non-secret run ID before execution. Keep this ownership record outside the disposable cluster. The workload tracks each successful Kubernetes create immediately, attempts every tracked delete in reverse dependency order even after an earlier error, and waits for observed Kubernetes deletion. `cleanup: auto` removes the action-owned kind environment after normal completion/failure; neither it nor Kubernetes NotFound proves that the remote BTP resource is absent.

If a run fails or is cancelled, inspect both sides before cleaning:

- In the dedicated BTP account, enumerate Subaccounts by exact `xp-btp-bench-<run-id>-<attempt>-` name prefix and matching `xpbtpbench-<run-id>-<attempt>-` subdomain. Enumerate Directories by their recorded exact generated display/name, then verify ownership using run identity and creation timing. Inspect the related CIS allocations and API credentials using the recorded run names and parent IDs. Never delete by a broad `xp` prefix or delete unrelated account contents.
- Keep the run ID, each exact generated Kubernetes name, remote Subaccount/Directory IDs, entitlement identifiers, and credential name in the trusted operator's private run record. Do not put secret values, API credential contents, connection Secret values, or diagnostic payloads in workflow logs or artifacts. The API credential is configured read-only; verify in BTP that the exact credential was revoked after deletion. If revocation cannot be confirmed, treat the run as failed and escalate to the account owner.
- If a kind environment is retained during runner cleanup, inspect only the specifically recorded objects in namespace `default` and their Crossplane conditions/finalizers before proceeding. The DirectoryEntitlement is cluster-scoped in the workload; use its exact recorded name.
- Kubernetes NotFound and a requested delete are not proof that the remote BTP resources were deleted. Verify remote absence/revocation after finalizers complete.

## Trusted fallback cleanup

Hard cancellation, runner loss, or a stuck cloud finalizer can bypass workload cleanup. An account owner or other trusted operator must perform fallback cleanup from a trusted workstation or a separately approved workflow whose cleanup implementation comes from the protected default branch, never from the PR checkout. Authenticate with the dedicated account credentials and use the protected, trusted procedure to enumerate exact run-owned objects. Independently confirm the run ID, generated names, parent references, and remote IDs before deleting anything. Delete dependent resources first: API credential (and verify remote revocation), Subaccount Entitlement and DirectoryEntitlement, then Directory and Subaccount. Record target IDs before deletion and poll the BTP account until each remote object/allocation is absent. If a finalizer or remote deletion is stuck, escalate to the account owner/provider support rather than removing unrelated Kubernetes state. Do not automatically delete by a user-supplied arbitrary prefix. Confirm the BTP technical user has the privileges needed to revoke the read-only API credential and the Directory admin is valid; both are required feasibility checks.

The workflow enables bounded provider-log diagnostics and collects managed-resource Events for DirectoryEntitlement, filtered by resource kind and run-specific name prefix. xp-diadromos rejects credential-kind Event selectors (including SubaccountApiCredential) to avoid collecting potentially sensitive Event content; SubaccountApiCredential errors are therefore covered only through sanitized provider-log categories. Immediately after an archive is produced and before report publication, it prints and adds to the GitHub Actions run summary a sanitized diagnostic summary: sidecar/log/Event completeness and dropped-record counts, categorized coverage warnings, Event kind/type/counts, reviewed Event reasons (including resource-reference resolution), and categorized provider errors. Unreviewed warning and reason strings collapse to fixed categories. Allowlisted provider-error categories distinguish Directory status validation, missing provider RBAC, resource-reference resolution, SubaccountApiCredential client-secret/state errors, BTP HTTP status classes, request timeouts, and transport failures. Provider error counts are split into the first 60 seconds and later capture time, relative to the first retained diagnostic log timestamp (not benchmark start); raw messages, identifiers, status text, warning text, and timestamps are omitted.

The workload also records per-resource phase markers and durations for the Kubernetes create request (requested/accepted), Ready observation, Kubernetes delete request (requested/accepted), and Kubernetes object absence observation. The report verifier adds only allowlisted kinds, phases, outcomes, categories, sample counts, and finite p50 durations to the job summary, in addition to the lifecycle contract matrix and missing-evidence annotations. These are Kubernetes/client observations: an accepted Kubernetes delete or an absent Kubernetes object does **not** establish remote BTP deletion. Summary generation is best-effort and does not block report publication. Never upload kubeconfigs, the provider package, archives, diagnostics, credentials, or output directories as part of cleanup. The workflow uploads only the report action's explicit JSON and Markdown report files (7-day retention). Review any downloaded report before sharing it; labels and context can identify private infrastructure.

## Local-versus-CI build comparison

The CI job builds and packages the checked-out reviewed SHA for Linux AMD64, then gives that package to xp-diadromos as `provider:v0`. The local debug script instead requires a caller-supplied provider `.xpkg`, assigns `provider:v0`, and does not verify that the package was built from the current worktree or the same SHA as CI. The local and CI configs use the same Crossplane version, k6 image, resource workload, ProviderConfig fields, and credential environment-variable names, but identical credential values alone do not establish provider-build parity. Before any approved live comparison, record and compare the local artifact's source SHA/build provenance with the reviewed CI SHA and confirm both package paths use the same provider code. Do not print credentials or inspect raw diagnostic messages in ordinary CI logs.

## Operational interpretation

The v0.7.1 k6 image and CLI are explicitly selected, and the package comes from the reviewed SHA. The five create/Ready/delete pairs execute serially with one VU and one iteration. The default 600-second readiness and deletion bounds imply at most 6,000 seconds (100 minutes) of lifecycle waits (five creates plus five deletes), plus API/setup/report overhead. That leaves 20 minutes below the 2-hour k6 wait limit and 80 minutes below the 180-minute job timeout; confirm the action's wait-timeout semantics include cleanup and setup before adopting these defaults. Account owners/operators must validate real per-kind timings and reduce suitable bounds or otherwise justify the job budget before enabling routine runs. Any timeout or partial cleanup fails visibly and requires remote reconciliation. CPU, memory, and Prometheus series are informational. No latency threshold, baseline, or policy is configured. Benchmark failures are not repaired by report publication: execution and reporting remain separate and either failure must remain visible.
