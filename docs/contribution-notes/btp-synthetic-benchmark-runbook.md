# BTP synthetic benchmark operations

The workflow `BTP synthetic benchmark` is report-only. It builds the exact reviewed provider revision and runs five serial create/Ready/delete observations for each of Subaccount, Directory, Entitlement, DirectoryEntitlement, and read-only SubaccountApiCredential against a **dedicated, explicitly approved SAP BTP test account**. Five independent parent sets are created in dependency order; all 25 managed resources coexist until every one has been observed Ready, then cleanup proceeds in reverse dependency order. The workload uses one VU, one iteration, and serial create requests. It is not a performance gate or a statistical performance test. A healthy report has `status: not_evaluated`; exactly five finite, uncensored samples per required lifecycle group are required, and missing/extra evidence or any known operation/cleanup failure fails the job.

## Required setup before enabling runs

1. Provision a dedicated BTP test account with capacity for five simultaneous Subaccounts, five Directories, five Subaccount `cis/local` entitlements, five Directory `cis/local` entitlements, and five read-only API credentials in region `eu10`. Confirm quota, allocation uniqueness, permissions, billing/cost responsibility, a human cleanup contact, and an exact-target fallback operator before enabling the five-instance workload. Directory requires two distinct admins; confirm both are valid users in the account. Confirm `cis/local` is available for all ten allocations without conflicts; any alternative must be approved by the account owner before changing the workload. Do not use a developer or production account.
2. The workflow intentionally runs `pull_request` benchmarks only for non-draft, same-repository PRs targeting the default branch. Fork PRs are skipped and receive no BTP or release secrets. Same-repository contributors are trusted to execute reviewed PR-head code with the dedicated test-account secrets under this model; the job checks out and asserts the event head SHA with `persist-credentials: false`. Manual dispatch is restricted to the default branch and requires explicit dedicated-account confirmation. Do not change these boundaries without a separate security review.
3. Configure the approved `pr-e2e-no-approval` environment with variables `GLOBAL_ACCOUNT` (the dedicated global account subdomain) and `CLI_SERVER_URL` (the BTP CLI server URL for that environment), and secrets `BTP_TECHNICAL_USER`, `CIS_CENTRAL_BINDING`, `TECHNICAL_USER_EMAIL`, `SECOND_DIRECTORY_ADMIN_EMAIL`, `XP_DIADROMOS_RELEASE_TOKEN`, and `BTP_ENV_COMPARE_HMAC_KEY`. The account subdomain must match the global account that owns the CIS central binding. The two admin email secrets must identify distinct, valid BTP users. Use the provider's established JSON credential formats. The release token should be a short-lived GitHub App installation token or fine-grained credential with only Contents: read on the private xp-diadromos repository. Generate `BTP_ENV_COMPARE_HMAC_KEY` as 32 random bytes encoded as 64 hex characters (for example, `openssl rand -hex 32`), store it as a GitHub environment secret, and provide the same key to an authorized local comparison through a secure secret manager. Do not print or commit the key. Fingerprints remain linkable while the key is reused, so rotate/remove it after comparison if ongoing correlation is not needed. Never put credential material into config, scripts, artifacts, or logs.
4. The workflow checks out the private xp-diadromos actions at full commit SHA `73918d847f254cef9bd123c11f777b76db9b0bea`. It independently selects execution CLI and k6 image `v0.8.0`, and report CLI `v0.8.1` for presentation display units. Confirm private action checkout and authenticated CLI release-asset installation in a trusted default-branch dispatch; access to the private repository and release assets are separate authorization checks.

## Resource ownership and discovery

Every workload object is named deterministically from the numeric `XP_DIADROMOS_BTP_RUN_ID`, numeric `XP_DIADROMOS_BTP_RUN_ATTEMPT` (default `1` locally), and instance index `1..5`; values are not timestamped or truncated. The run ID must contain 1–20 decimal digits and the attempt 1–10 decimal digits. CI supplies the GitHub run ID/attempt. For a local run, choose a unique numeric run ID and attempt; reusing them deliberately targets the same names. Reconstruct each name after runner loss using identity `<run-id>-<attempt>-<instance>` and these prefixes: Subaccount `xp-btp-bench-`, Directory `xp-btp-bench-dir-`, Entitlement `xp-btp-bench-ent-`, DirectoryEntitlement `xp-btp-bench-dirent-`, SubaccountApiCredential/connection Secret `xp-btp-bench-api-` (append `-secret` for the Secret), and Subaccount subdomain `xpbtpbench-`. For each index, its Entitlement and API credential reference that index's Subaccount, and its DirectoryEntitlement references that index's Directory. Keep the run ID, attempt, exact names, and indexed parent relationships in the trusted operator's private run record; add remote BTP IDs as they become available. Do not upload ownership records. The workflow serializes all dispatches and eligible PR runs for the shared dedicated account and does not cancel an active run; GitHub may replace an older pending run when another run queues, so do not rely on pending runs being FIFO. The workload tracks each accepted Kubernetes create immediately, retains all resources through the all-ready marker, attempts every tracked delete in reverse dependency order even after an earlier error, and waits for observed Kubernetes deletion. `cleanup: auto` removes the action-owned kind environment after normal completion/failure; neither it nor Kubernetes NotFound proves that the remote BTP resource is absent.

If a run fails or is cancelled, inspect both sides before cleaning:

- In the dedicated BTP account, enumerate only the five exact indexed Subaccount names and matching subdomains in the private ownership record. Enumerate the five Directories by their exact generated names/display names, then verify ownership using run identity and creation timing. Inspect all ten CIS allocations and five API credentials using recorded names and parent IDs. Never delete by a broad `xp` prefix or delete unrelated account contents.
- Keep the run ID, all 25 exact generated Kubernetes names, five remote Subaccount IDs, five Directory IDs, ten entitlement identifiers, and five credential names in the trusted operator's private run record. Do not put secret values, API credential contents, connection Secret values, or diagnostic payloads in workflow logs or artifacts. All five API credentials are configured read-only; verify each exact credential was revoked after deletion. If any revocation cannot be confirmed, treat the run as failed and escalate to the account owner.
- If a kind environment is retained during runner cleanup, inspect only the specifically recorded objects in namespace `default` and their Crossplane conditions/finalizers before proceeding. The DirectoryEntitlement is cluster-scoped in the workload; use its exact recorded name.
- Kubernetes NotFound and a requested delete are not proof that the remote BTP resources were deleted. Verify remote absence/revocation after finalizers complete.

## Trusted fallback cleanup

Hard cancellation, runner loss, or a stuck cloud finalizer can bypass workload cleanup. An account owner or other trusted operator must perform fallback cleanup from a trusted workstation or a separately approved workflow whose cleanup implementation comes from the protected default branch, never from the PR checkout. Authenticate with the dedicated account credentials and use the protected, trusted procedure to enumerate exact run-owned objects. Independently confirm the run ID, generated names, parent references, and remote IDs before deleting anything. Delete dependent resources first: API credential (and verify remote revocation), Subaccount Entitlement and DirectoryEntitlement, then Directory and Subaccount. Record target IDs before deletion and poll the BTP account until each remote object/allocation is absent. If a finalizer or remote deletion is stuck, escalate to the account owner/provider support rather than removing unrelated Kubernetes state. Do not automatically delete by a user-supplied arbitrary prefix. Confirm the BTP technical user has the privileges needed to revoke the read-only API credential and the Directory admin is valid; both are required feasibility checks.

The benchmark does not collect or print provider diagnostics, Kubernetes Events, or resource-readiness snapshots. The workflow publishes only the explicitly reviewed benchmark report files.

`benchmarks/btp/fingerprint-env.py` prints keyed HMAC fingerprints and coarse byte-length buckets for allowlisted provider inputs, without printing their values. JSON objects are canonicalized before fingerprinting, and selected authentication fields are fingerprinted individually to help locate mismatches. The same separately generated `BTP_ENV_COMPARE_HMAC_KEY` is needed for local and CI outputs to be comparable; do not use plain hashes for credentials. Fingerprints reveal equality and remain linkable while the key is reused, so restrict log access and rotate the key after comparison when appropriate.

The workload records per-instance lifecycle points grouped only by resource kind, plus phase markers and durations for Kubernetes create/readiness/delete operations and Kubernetes object absence. These are Kubernetes/client observations: an accepted Kubernetes delete or an absent Kubernetes object does **not** establish remote BTP deletion. The report verifier checks the lifecycle contract and fails on missing evidence. Benchmark execution and report publication are separate steps; an available archive can be reported after an execution failure without masking its status. The workflow uploads only the selected finalized metrics archive as a named seven-day artifact and only the report action's explicit JSON and Markdown files as a separate seven-day artifact. Never upload kubeconfigs, the provider package, diagnostics, credentials, or output directories. Review any downloaded report/archive before sharing; labels and context can identify private infrastructure, and archive diagnostics remain disabled.

## Dashboard interpretation and private archive replay

The overview dashboard uses projected k6 observation gauges for iteration duration, readiness, and the Kubernetes-object-absence endpoint. These values represent occupied projection buckets; Prometheus lookback can carry the last value forward between source samples. They are **last-observed bucket durations**, not a continuous event stream, and iteration count is a completed-count counter—not throughput. Do not derive a full-run mean from the dashboard `_mean` gauges. The PR report's raw-k6 aggregates are the supported full-run summaries. Existing archives keep their embedded dashboard; `metrics stats --dashboard benchmarks/btp/perses/overview.yaml` overrides dashboard-scoped interpretation for local replay without changing archive bytes.

Provider reconciliation duration and workqueue waiting duration are five-minute rate-of-sum divided by rate-of-count means, shown in seconds. They summarize individual reconciliation execution or time waiting in a queue; neither is client-observed Ready latency. A window with no histogram observations has no measured mean; it must not be interpreted as zero. Workqueue depth is a sampled gauge (summing priority series for each controller), so gaps between samples do not prove the queue was empty. These controller panels are restricted to the five benchmark resource controllers and retain `archive_filename` so runs are not pooled.

Lifecycle phase panels separate client-observed Kubernetes create/delete request acceptance from readiness and Kubernetes-object-absence waits. They show stage and outcome; request acceptance and object absence do not establish remote BTP API latency or remote deletion. Phase means are projected sparse gauges with the same lookback caveat as the other k6 observations. The external-operation panel is supplementary Upjet instrumentation grouped only by operation and archive, with a five-minute mean in seconds. Coverage is partial, has no resource-kind attribution, and `connect` must not be assumed to represent a remote HTTP request. Missing series remain missing rather than being inferred or backfilled.

The PR report retains provider CPU/memory samples and lifecycle means, and adds the complete-iteration duration, per-kind readiness medians, and observed reconciliation-error increases for the five exercised controllers. The report CLI's supported display units keep CPU and memory readable; durations remain in milliseconds. Readiness statistics are based on five samples per kind and are descriptive, not high-confidence percentiles. Reconciliation errors are observed counter increases, not a failure threshold; a nonzero count alone does not fail an otherwise successful report. The table does not imply continuous throughput, remote API latency, or proof of remote BTP deletion.

An explicit, offline-first replay utility is available for trusted CLI binaries and a caller-approved archive. It requires an already-existing private output directory, checks CLI versions, writes query/report results only there, serves the archive on loopback, and terminates the server on completion or failure. It does not install tools, discover credentials, start clusters, publish comments, or upload data. Never place an archive, report, or query output in the repository or a publication artifact. The acceptance replay requires the published execution CLI v0.8.0 and report CLI v0.8.1; synthetic tests do not replace pinned-release compatibility. For example:

```bash
mkdir -m 700 /tmp/btp-metrics-replay
python3 benchmarks/btp/validate-metrics-archive.py \\
  --report-cli /path/to/xp-diadromos-v0.8.1 \\
  --execution-cli /path/to/xp-diadromos-v0.8.0 \\
  --archive /private/path/approved.tsdb.tar.zst \\
  --output-dir /tmp/btp-metrics-replay
```

This check does not establish visual correctness. Inspect the dashboard with the supported pinned Perses renderer on a capable host, confirm the single iteration sample is visible, and note its lookback persistence and evaluation resolution. Existing archives need an explicitly supported Perses import to preview changed dashboard bytes; the stats override does not rewrite the archive's embedded dashboard. Pinned CLI replay and visual acceptance are separate gates. Neither requires a live BTP run.

## Local-versus-CI build comparison

The CI job builds and packages the checked-out reviewed SHA for Linux AMD64, then gives that package to xp-diadromos as `provider:v0`. The local debug script instead requires a caller-supplied provider `.xpkg`, assigns `provider:v0`, and does not verify that the package was built from the current worktree or the same SHA as CI. The local and CI configs use the same Crossplane version, k6 image, resource workload, ProviderConfig fields, and credential environment-variable names, but identical credential values alone do not establish provider-build parity. Before any approved live comparison, record and compare the local artifact's source SHA/build provenance with the reviewed CI SHA and confirm both package paths use the same provider code. Do not print credentials or inspect raw diagnostic messages in ordinary CI logs.

## Operational interpretation

The v0.8.0 execution CLI and k6 image and v0.8.1 report CLI are explicitly selected, and the provider package comes from the checked-out reviewed SHA. The 25 create/Ready/delete sequences execute serially with one VU and one iteration; all 25 resources remain present until the final Ready observation. Each resource has a 600-second readiness and deletion cap. Aggregate readiness polling is bounded by a 2,700-second creation budget; cleanup has an independent 3,000-second reservation, so worst-case polling allowance is 95 minutes. The scenario allows 110m (95 minutes plus 15 minutes of request/iteration headroom), the CLI TestRun wait allows 2h, and the GitHub job allows 180 minutes for the wait plus setup/build/report overhead. These are repository-configured candidate bounds, not measured timings, performance thresholds, or wall-clock guarantees. Absolute JS deadlines bound polling only: a blocking xk6 request may exceed them, and hard cancellation/runner loss can interrupt cleanup. The functional `xp_lifecycle_success` Rate threshold (`rate==1`) makes validation, create/readiness, and cleanup failures fail k6; it is not a latency/performance policy. Account owners/operators must validate real timings and pinned-image/CLI failure propagation on a trusted host before routine use. An expired cleanup budget still issues each remaining delete request but cannot claim observed absence; use trusted fallback reconciliation. The action's archive upload preserves benchmark failure visibility; it does not imply a successful lifecycle or cleanup. Any timeout or partial cleanup fails visibly and requires remote reconciliation. CPU, memory, and Prometheus series are informational. No latency threshold, baseline, or policy is configured. Benchmark failures are not repaired by report publication: execution and reporting remain separate and either failure must remain visible.
