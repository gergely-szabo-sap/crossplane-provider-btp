# BTP synthetic benchmark operations

The workflow `BTP synthetic benchmark` is report-only. It builds the exact reviewed provider revision and runs one serial create/Ready/delete observation for each of Subaccount, Directory, Entitlement, DirectoryEntitlement, and SubaccountApiCredential against a **dedicated, approved SAP BTP test account**. This is currently one instance per kind; all five coexist until the serial create/readiness pass completes, then cleanup proceeds in reverse dependency order. It is not a performance gate or a statistical performance test. A healthy report has `status: not_evaluated`; missing lifecycle evidence or any operation/cleanup failure fails the job. Any expansion beyond this one-set workload requires the account-owner and trusted-host acceptance gates in `btp-multi-resource-benchmark-plan.md`.

## Required setup before enabling runs

1. Provision a dedicated BTP test account with sufficient Subaccount, Directory, entitlement, and credential quotas in region `eu10`. Confirm account permissions, billing responsibility, a human cleanup contact, and conservative per-resource limits. Directory requires two distinct admins; confirm both are valid users in the account. Confirm `cis/local` is available for both Subaccount and Directory entitlements without allocation conflicts; choose another account-owner-approved low-cost plan or defer the relevant test if it is not. Do not use a developer or production account.
2. The workflow intentionally runs `pull_request` benchmarks only for non-draft, same-repository PRs targeting the default branch. Fork PRs are skipped and receive no BTP or release secrets. Same-repository contributors are trusted to execute reviewed PR-head code with the dedicated test-account secrets under this model; the job checks out and asserts the event head SHA with `persist-credentials: false`. Manual dispatch is restricted to the default branch and requires explicit dedicated-account confirmation. Do not change these boundaries without a separate security review.
3. Configure the approved `pr-e2e-no-approval` environment with variables `GLOBAL_ACCOUNT` (the dedicated global account subdomain) and `CLI_SERVER_URL` (the BTP CLI server URL for that environment), and secrets `BTP_TECHNICAL_USER`, `CIS_CENTRAL_BINDING`, `TECHNICAL_USER_EMAIL`, `SECOND_DIRECTORY_ADMIN_EMAIL`, `XP_DIADROMOS_RELEASE_TOKEN`, and `BTP_ENV_COMPARE_HMAC_KEY`. The account subdomain must match the global account that owns the CIS central binding. The two admin email secrets must identify distinct, valid BTP users. Use the provider's established JSON credential formats. The release token should be a short-lived GitHub App installation token or fine-grained credential with only Contents: read on the private xp-diadromos repository. Generate `BTP_ENV_COMPARE_HMAC_KEY` as 32 random bytes encoded as 64 hex characters (for example, `openssl rand -hex 32`), store it as a GitHub environment secret, and provide the same key to an authorized local comparison through a secure secret manager. Do not print or commit the key. Fingerprints remain linkable while the key is reused, so rotate/remove it after comparison if ongoing correlation is not needed. Never put credential material into config, scripts, artifacts, or logs.
4. The workflow checks out the private xp-diadromos actions at full commit SHA `73918d847f254cef9bd123c11f777b76db9b0bea`. It independently selects execution CLI and k6 image `v0.8.0`, and report CLI `v0.8.1` for presentation display units. Confirm private action checkout and authenticated CLI release-asset installation in a trusted default-branch dispatch; access to the private repository and release assets are separate authorization checks.

## Resource ownership and discovery

Every workload object is named with a run-unique suffix derived from the explicit `XP_DIADROMOS_BTP_RUN_ID`, attempt, and timestamp. The Subaccount uses `xp-btp-bench-` plus that suffix and the BTP subdomain uses `xpbtpbench-`; Directory, both entitlements, the API credential, and its generated connection Secret each have distinct names containing the same suffix. The Directory display name is run-unique. Find the GitHub run ID/attempt in the workflow URL or run summary; for local runs record the supplied non-secret run ID before execution. Keep this ownership record outside the disposable cluster. The workload tracks each successful Kubernetes create immediately, attempts every tracked delete in reverse dependency order even after an earlier error, and waits for observed Kubernetes deletion. `cleanup: auto` removes the action-owned kind environment after normal completion/failure; neither it nor Kubernetes NotFound proves that the remote BTP resource is absent.

If a run fails or is cancelled, inspect both sides before cleaning:

- In the dedicated BTP account, enumerate Subaccounts by exact `xp-btp-bench-<run-id>-<attempt>-` name prefix and matching `xpbtpbench-<run-id>-<attempt>-` subdomain. Enumerate Directories by their recorded exact generated display/name, then verify ownership using run identity and creation timing. Inspect the related CIS allocations and API credentials using the recorded run names and parent IDs. Never delete by a broad `xp` prefix or delete unrelated account contents.
- Keep the run ID, each exact generated Kubernetes name, remote Subaccount/Directory IDs, entitlement identifiers, and credential name in the trusted operator's private run record. Do not put secret values, API credential contents, connection Secret values, or diagnostic payloads in workflow logs or artifacts. The API credential is configured read-only; verify in BTP that the exact credential was revoked after deletion. If revocation cannot be confirmed, treat the run as failed and escalate to the account owner.
- If a kind environment is retained during runner cleanup, inspect only the specifically recorded objects in namespace `default` and their Crossplane conditions/finalizers before proceeding. The DirectoryEntitlement is cluster-scoped in the workload; use its exact recorded name.
- Kubernetes NotFound and a requested delete are not proof that the remote BTP resources were deleted. Verify remote absence/revocation after finalizers complete.

## Trusted fallback cleanup

Hard cancellation, runner loss, or a stuck cloud finalizer can bypass workload cleanup. An account owner or other trusted operator must perform fallback cleanup from a trusted workstation or a separately approved workflow whose cleanup implementation comes from the protected default branch, never from the PR checkout. Authenticate with the dedicated account credentials and use the protected, trusted procedure to enumerate exact run-owned objects. Independently confirm the run ID, generated names, parent references, and remote IDs before deleting anything. Delete dependent resources first: API credential (and verify remote revocation), Subaccount Entitlement and DirectoryEntitlement, then Directory and Subaccount. Record target IDs before deletion and poll the BTP account until each remote object/allocation is absent. If a finalizer or remote deletion is stuck, escalate to the account owner/provider support rather than removing unrelated Kubernetes state. Do not automatically delete by a user-supplied arbitrary prefix. Confirm the BTP technical user has the privileges needed to revoke the read-only API credential and the Directory admin is valid; both are required feasibility checks.

The benchmark does not collect or print provider diagnostics, Kubernetes Events, or resource-readiness snapshots. The workflow publishes only the explicitly reviewed benchmark report files.

`benchmarks/btp/fingerprint-env.py` prints keyed HMAC fingerprints and coarse byte-length buckets for allowlisted provider inputs, without printing their values. JSON objects are canonicalized before fingerprinting, and selected authentication fields are fingerprinted individually to help locate mismatches. The same separately generated `BTP_ENV_COMPARE_HMAC_KEY` is needed for local and CI outputs to be comparable; do not use plain hashes for credentials. Fingerprints reveal equality and remain linkable while the key is reused, so restrict log access and rotate the key after comparison when appropriate.

The workload records per-resource phase markers and durations for Kubernetes create/readiness/delete operations and Kubernetes object absence. These are Kubernetes/client observations: an accepted Kubernetes delete or an absent Kubernetes object does **not** establish remote BTP deletion. The report verifier checks the lifecycle contract and fails on missing evidence. Benchmark execution and report publication are separate steps; an available archive can be reported after an execution failure without masking its status. The workflow uploads only the selected finalized metrics archive as a named seven-day artifact and only the report action's explicit JSON and Markdown files as a separate seven-day artifact. Never upload kubeconfigs, the provider package, diagnostics, credentials, or output directories. Review any downloaded report/archive before sharing; labels and context can identify private infrastructure, and archive diagnostics remain disabled.

## Local-versus-CI build comparison

The CI job builds and packages the checked-out reviewed SHA for Linux AMD64, then gives that package to xp-diadromos as `provider:v0`. The local debug script instead requires a caller-supplied provider `.xpkg`, assigns `provider:v0`, and does not verify that the package was built from the current worktree or the same SHA as CI. The local and CI configs use the same Crossplane version, k6 image, resource workload, ProviderConfig fields, and credential environment-variable names, but identical credential values alone do not establish provider-build parity. Before any approved live comparison, record and compare the local artifact's source SHA/build provenance with the reviewed CI SHA and confirm both package paths use the same provider code. Do not print credentials or inspect raw diagnostic messages in ordinary CI logs.

## Operational interpretation

The v0.8.0 execution CLI and k6 image and v0.8.1 report CLI are explicitly selected, and the provider package comes from the checked-out reviewed SHA. The five create/Ready/delete pairs execute serially with one VU and one iteration. The default 600-second readiness and deletion bounds imply at most 6,000 seconds (100 minutes) of lifecycle polling (five creates plus five deletes), plus API/setup/report overhead. The scenario allows 1h, the CLI TestRun wait allows 2h, and the GitHub job allows 180 minutes; these bounds are not additive guarantees, and request/setup/cleanup behavior must be validated on a trusted host. Account owners/operators must validate real per-kind timings before routine runs. The action's archive upload preserves benchmark failure visibility; it does not imply a successful lifecycle or cleanup. Any timeout or partial cleanup fails visibly and requires remote reconciliation. CPU, memory, and Prometheus series are informational. No latency threshold, baseline, or policy is configured. Benchmark failures are not repaired by report publication: execution and reporting remain separate and either failure must remain visible.
